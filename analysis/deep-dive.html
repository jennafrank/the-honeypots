How the dominant family persists

The stdin-to-file → cron family (4,055 sessions, 600+ sources) uses a layered persistence strategy:

1 File write via stdin: cat > "w.sh" && chmod +x w.sh — payload piped over the SSH channel, never downloaded 2 Cron persistence: @reboot + hourly crontab entry with grep -F idempotency check — survives reboot, runs without SSH session 3 Systemd user unit: watcher-netai.service enabled via systemctl --user enable --now — a second persistence path independent of cron 4 Competitor cleanup: kill -9 + crontab -l | grep -v . | crontab - — wipes other actors' crontabs after installing its own
Detection insight: A cron-only detection catches the persistence but misses the systemd unit. The crontab wipe (F2) is the same file-write event as the install — schedule changed, not persistence added. Telling them apart needs before/after crontab content.
