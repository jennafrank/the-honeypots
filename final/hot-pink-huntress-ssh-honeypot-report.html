// TL;DR — FIVE THINGS TO KNOW

  • The lure didn't matter. 147 days as a "Solana validator" and 136,128 sessions later — only 5 found the fake wallet. Attackers treated this box as generic Linux compute.
  • Automation dominates. 96.6% of sessions ran zero or one command. The internet runs on scripts, not humans.
  • The main goal was crypto mining, not Solana keys. 3,692 sessions deployed a miner. 5 looked for wallet files.
  • They came back. 95.5% of sessions came from IPs that had connected before. One successful brute-force doesn't generate one intrusion — it generates a subscription.
  • Turn off SSH password auth. Every session in this dataset succeeded because the honeypot accepted every credential. Public-key-only authentication would have stopped all of it.

Pre-Investigation Notes

Five addresses were excluded from all metrics in this report: four operator-controlled addresses (including loopback) and one friend who knew about the project and tested it.

Section 1Executive Summary

For 147 calendar days, a server sat on the open internet with SSH port 22 exposed, pretending to be a Solana cryptocurrency validator node. It accepted every login attempt automatically, logged every command, and said nothing. No real data was at risk. The point was to watch: who shows up, what do they want, and how do they behave once they think they're in?

Over that period, 6,145 unique IP addresses knocked on the door. They generated 136,128 sessions, tried 63,283 distinct username-and-password combinations, and issued 414,070 commands after gaining access. The server was hit with an average of 926 sessions every single day. The moment the honeypot went live, the first attacker arrived. Not hours later. The moment it went live.

The attackers were not, for the most part, sophisticated human hackers typing commands one by one. The vast majority of activity came from automated tools running credential wordlists and deployment scripts. The goal in most cases was cryptocurrency mining: get in, kill any competing miner already running, drop a new miner binary, set up persistence via cron and systemd, and leave. A smaller subset of sessions existed to validate whether a credential worked, with no exploitation attempted at all. At the far end of the spectrum, a handful of sessions showed genuine human operators conducting methodical reconnaissance and attempting to plant persistent backdoors.

The single most actionable takeaway from this dataset: disable password-based SSH authentication. Nearly every session in this report was possible because the server accepted a password login (560 attempted public-key auth). Switch to SSH key authentication, and the attack surface for all of this activity drops to near zero.

Section 2Methodology

The decoy. The server presented itself as a Solana blockchain validator node. The SSH banner, fake filesystem layout, and simulated process list all reinforced this fiction. User accounts named sol and solana appeared in the environment. The goal was to make the server look like it was running real Solana validator software, to see whether attackers would behave differently toward a known crypto-infrastructure target.

Tech stack. The honeypot ran on an Azure virtual machine. A custom Python SSH server (built on the asyncssh library) accepted all incoming connections, simulated a Linux shell, and logged every credential attempt and every command to a SQLite database. The shell responses were scripted to look plausible without executing anything real.

Run period. April 27, 2026 through September 21, 2026. 147 calendar days.

Credential acceptance. Every username and password combination was accepted. Attackers were never told their credentials were wrong. This is standard honeypot practice: rejection teaches the attacker nothing useful happened, while acceptance draws them deeper and reveals behavior.

Term definitions.
- Session: A single SSH connection from authentication through disconnect.
- Connection: Used interchangeably with session throughout this report.
- Return visitor: An IP address that created more than one session over the run period.
- High-interest session: A session that triggered one or more behavioral flags indicating substantive attacker activity beyond a simple credential probe.
- Easter egg: A named behavioral trap embedded in the simulated environment. Specific commands or actions trigger these flags, which are used to classify attacker intent and depth.

Operator exclusions. As noted above, five addresses are excluded from all metrics.

Playtester. One visitor on day 2 found the easter egg — a playable terminal game launched by typing top — and died six times in four minutes. Their sessions have been excluded from all metrics in this report. They knew about the project.

AbuseIPDB limitation. This report does not include AbuseIPDB reputation data. The honeypot database was not populated with AbuseIPDB lookups during the run period, so abuse scores are unavailable for cross-referencing.

The honeypot recorded its first session at 23:09:48 UTC on April 27, 2026. The IP was 2[.]57[.]122[.]238, geolocated to Amsterdam, Netherlands, operating on AS47890 (Unmanaged LTD). The attacker used username sol and password 12345678. Within seconds of gaining access, the session issued four commands:

/bin/./uname -s -v -n -r -m
uptime -p
lspci | grep VGA
nvidia-smi -q

The first two are standard reconnaissance. The last two are GPU enumeration. lspci | grep VGA lists graphics cards. nvidia-smi -q queries NVIDIA GPU status and driver information. This attacker was not looking for Solana tooling. The attacker was hunting for GPU compute capacity to mine cryptocurrency. The server had been live for less than a minute.

The 95.5% return-visitor rate deserves special note. Only 4.5% of sessions in this dataset came from an IP that had never connected before. The other 95.5% came from IPs that had connected at least once previously — 129,956 sessions (95.5%). This is not loyalty. It is scripted re-scanning. Automated tools log working credentials and return to them. 3,830 of the 6,145 unique attacker IPs returned at least once. The implication for defenders is that a successful brute-force attempt does not generate one intrusion event. It generates dozens or hundreds.

4d. The Credential-Validation Wave

On May 22, 2026, between 02:46 and 10:56 UTC, IP address 38[.]58[.]169[.]236 (AS174 Cogent Communications, geolocated to Mexico) created 8,949 sessions over 8 hours and 10 minutes. Every single session followed an identical pattern: one command, the credential-validation ping:

echo -e "\x6F\x6B"

This outputs the string ok. Nothing else. No reconnaissance. No payload. No persistence.

This is not an attack. It is a quality-assurance sweep. The operator had a list of credentials and wanted to confirm which ones still worked. Each session connected, sent the ping, confirmed the shell responded, and disconnected. The result is a verified list of live credentials — which can feed exploitation tooling, or be sold on underground markets where buyers pay for confirmed working logins rather than raw wordlists.

This wave accounts for 8,949 of the 63,364 total echo -e "\x6F\x6B" commands in the dataset. It is also why the previous report's analysis showed an artifact peak in the 02:00 to 10:00 UTC window. Once this single IP is excluded, the hourly distribution shifts (detailed in Section 6).

5b. Three Tiers of Attacker Behavior

The 136,128 sessions split into four clean, non-overlapping tiers by command count. All four sum to the total.

Tier 1: Silent authenticators — 66,692 sessions (49.0%). These sessions connect, authenticate, run zero commands, and disconnect. The shell never received a single keystroke. These are pure credential probers: the tool confirms the password works and logs the result for later. Nothing was deployed; nothing was enumerated. Nearly half the dataset is this.

Tier 2: Single-command validators — 64,339 sessions (47.3%). One command, then gone. The canonical example is the 38[.]58[.]169[.]236 wave (8,949 sessions of echo -e "\x6F\x6B") — a liveness check that confirms the shell is interactive. Other single-command sessions run uname -a or id. The goal is credential validation, not exploitation. Tiers 1 and 2 together account for 131,031 sessions — 96.3% of all activity.

Tier 3: Active recon and escalation — 1,073 sessions (0.8%). Two to twenty commands: directory exploration, process enumeration, network configuration review, credential harvesting from /etc/passwd and /etc/shadow. Some sessions attempt to establish persistent access through SSH key injection or account creation. Small in count, high in intent. A subset of these sessions show timing and behavioral signals consistent with human operators — see the Hands on the Keyboard section.

Tier 4: Deployment campaigns — 4,024 sessions (3.0%). More than 20 commands. This tier is dominated by the 93-command miner script (3,210 sessions): it deploys a cryptocurrency miner binary, sets cron and systemd persistence, and runs a kill-competitor loop. Within Tier 4 sits the French backdoor session — 44 commands in the first 80 seconds (connection remained open for 10 hours) — and the 383 sessions that wrote SSH authorized keys. Easter egg triggers provide a behavioral signal within this tier: 4,124 distinct sessions (spanning Tiers 3 and 4) triggered at least one trap. Among specific traps, 3,693 sessions triggered run_payload, 3,643 triggered chmod_exe, 311 triggered passwd_harvest, and 5 reached the crown_jewel wallet trap.

Section 8Notable Sessions

8a. The French Backdoor Factory

Session ID 2b0e14c1 arrived on June 18, 2026 at 11:09 UTC from IP 212[.]112[.]19[.]166, registered to Glesys AB on AS42708 in Finland. The session ran 44 commands over its lifetime, making it one of the most command-dense sessions in the dataset.

The first phase was standard reconnaissance. The attacker checked system information, verified the current user context, explored the directory structure, and confirmed network configuration. Nothing unusual. Then the attacker pasted a multi-part shell payload written in French.

The payload was structured with labeled sections. DÉTECTION OS ran conditional checks to identify whether the system was running FreeBSD, a Debian-based distribution, or a Red Hat-based distribution. Each branch executed the correct commands for that OS family. CRÉATION DES UTILISATEURS created two hidden user accounts. The first was sys_admin with its home directory set to /var/.sys_admin. The second was r00t with its home directory at /var/.sys_temp. Both accounts received the password Hackers666. Both were added to the sudo group on Debian-based systems and the wheel group on Red Hat-based systems, giving them full administrative privileges. DOSSIERS + PERMISSIONS created the hidden home directories and set appropriate ownership. NETTOYAGE SILENCIEUX (silent cleanup) disabled bash history for both accounts by setting HISTFILE=/dev/null and HISTSIZE=0, ensuring no commands run under those accounts would be logged.

The entire payload was constructed to produce no stdout output. Every command was redirected to /dev/null or suppressed. An observer watching terminal output would see nothing happen.

This session scored 8 on the dataset's internal severity scale, the highest assigned score. The execution was automated — all 44 commands fired in under 80 seconds from a standard recon template — but the payload itself was clearly hand-crafted: full French-language inline comments, multi-distribution OS detection logic, and proper error handling. Most commodity attack tooling is written in English and pulled from shared repositories. This script reads like something built by a specific operator for their own use. The attacker demonstrated awareness of stealth techniques (hidden directories in /var, suppressed output, history deletion) and privilege escalation paths across multiple Linux distributions. The automation means this operator was not typing in real time, but someone did the engineering work.

8b. The Miner Eviction Squad

3,210 sessions across multiple source IPs ran an identical 93-command script. The script's internal logic is consistent enough that it almost certainly originated from a shared source: a GitHub repository, an underground forum post, or a direct toolkit transfer between operators.

The script executes in a fixed sequence. First, uname and related commands fingerprint the system. Second, the script searches for a writable directory, with /dev/shm as the preferred target (it is an in-memory filesystem, meaning the dropped files do not touch disk and are invisible to disk-based monitoring tools). Third, the script writes w.sh inline using cat with a heredoc, then runs chmod +x w.sh to make it executable. Fourth, the script establishes two persistence mechanisms: a crontab entry and a systemd unit file named watcher-netai.service. The systemd unit watches for the miner process and restarts it if killed. Fifth, the script runs a kill-competitor loop, repeating 12 or more times: readlink -f /proc/root/exe followed by kill -9 root, then readlink -f /proc/solana/exe followed by kill -9 solana. Finally, the script drops a binary named astats into /dev/shm.

The kill -9 solana command requires context. The miner script does not know the Solana service PID directly. Instead, it reads usernames from the fake ps aux output — "root" and "solana" — and passes them to both readlink -f /proc/<username>/exe and kill -9 <username>. On real Linux, /proc/ directories are numbered by PID, so /proc/solana/exe does not exist and kill -9 solana (which expects a numeric PID) would fail. These commands are a honeypot artifact: the custom fake shell responded to /proc/root/exe and /proc/solana/exe as if they were valid paths, producing logged output that doesn't reflect what would happen on a real target. On actual compromised servers, this script correctly resolves numeric PIDs from ps output. The kill loop is generic competitor-eviction — any miner running as a user named "solana" would be targeted, regardless of whether Solana-the-blockchain is involved.

The astats binary name is an indicator of compromise. Any server with an astats binary in /dev/shm or another temp-filesystem location should treat it as a strong signal of this campaign.

8c. The First Knock

At 23:09:48 UTC on April 27, 2026, the honeypot recorded its first session. The server had been live for less than a minute. The IP was 2[.]57[.]122[.]238, geolocated to Amsterdam, Netherlands, on AS47890 (Unmanaged LTD). The attacker used username sol and password 12345678.

The four commands in the session tell a clear story:

/bin/./uname -s -v -n -r -m
uptime -p
lspci | grep VGA
nvidia-smi -q

The first command uses an unusual path (/bin/./uname) that may reflect an attempt to evade command-logging tools that filter on exact command strings. The output contains kernel version, hostname, and architecture. The second command checks system uptime. The third queries PCI hardware for VGA/GPU devices. The fourth runs NVIDIA's system management interface in full query mode, returning detailed information about GPU drivers, memory, temperature, and utilization.

This attacker was GPU hunting. The server's Solana validator fiction may have drawn this specific session, as the attacker used username sol. However, Solana validators do not require GPU hardware — this session was hunting for cryptocurrency mining capacity generally. The speed of this first contact, under 60 seconds from server launch, reflects the density of automated scanning on the public internet. A new server on port 22 does not get hours to settle in. It gets seconds.

The ASN AS47890 (Unmanaged LTD) appears throughout this dataset. Three high-volume IPs from AS47890 are among the top IOC entries in Section 10 (2[.]57[.]121[.]25, 2[.]57[.]121[.]112, and 193[.]46[.]255[.]86), along with 2[.]57[.]122[.]238 — the very first attacker, which contributed a single session. Together this ASN produced 7,218 total sessions. The first session was the first of many from this network.

Section 9Hands on the Keyboard

Most of what happens in this dataset is automation on top of automation: scanners finding open ports, tools validating credentials, scripts running the same 93 commands in sequence. But a small number of sessions have timing, behavior, and mistakes that point to a human being at the other end. Here are the ones worth naming.

Methodology: sessions were scored on five signals — inter-command timing variance, shell escape attempts, typos and corrections, reactive navigation (commands that reference output from prior responses), and behavioral uniqueness. Timing was computed from the events table timestamps. All sessions below were reviewed command-by-command. Confidence labels are: "likely human or AI-driven agent" where timing is consistent but automation cannot be ruled out; "likely human" where multiple non-timing signals converge. IPs on residential and business ISPs are withheld; only ISP and region are shown.

The Explorer — Washington DC metro area, Verizon FiOS

Sessions: 21 visits on June 16, 2026, plus two later returns. ISP: Verizon Business FiOS, Washington DC metro area. Confidence: likely human or AI-driven agent.

The same source connected 21 times in six hours, always as labuser with passwords that progressively shortened: password123 → wer → nn → n → f → d → g → (empty) → a. Someone was iterating on logins, learning what the server would accept. On the first visit, three commands in: cat wallet.json. Crown jewel. Then they came back.

Subsequent sessions show systematic exploration. They read README.txt, checked .bash_history and .ssh/authorized_keys, examined cron entries and systemd units, and spent three separate sessions on DO_NOT_OPEN.zip — first using Python's chr() mapping to extract printable characters, then reading raw binary, then running a hex-encoded import os; os.system('ls -la /') to try to break out of the shell through Python.

They also probed the shell environment directly: echo $PROMPT_COMMAND, unset PROMPT_COMMAND, echo $TMOUT, export TMOUT=0. Then tried /bin/bash --norc --noprofile to spawn a different shell. The session stayed 5 minutes past each attempt with no success, then reconnected and tried something else.

Timing: Across 105 inter-command gaps in all sessions — minimum 0.0 s (multi-line commands logged separately), median 12.7 s, mean 29.2 s, max 175.6 s, stdev 38.3 s. The distribution is consistent with a person reading output and deciding what to try next, though a sufficiently agentic system could also produce this pattern.

Easter eggs triggered: crown_jewel, self_destruct (twice), dare_zip (three times), python_repl (six times).

Sidebar: The Bots That Checked for Honeypots

Not human — but worth a mention. A campaign of 382 sessions (from multiple source IPs, including 128[.]24[.]160[.]229) ran an automated recon script that explicitly tested for Cowrie, the most commonly deployed SSH honeypot:

ls /opt/cowrie /home/richard /etc/cowrie 2>&1   # Cowrie default paths (/home/richard is Cowrie's fake-filesystem default user)
test -f /.dockerenv                              # Docker container check
test -f /run/.containerenv                       # Podman container check

This is a Cowrie-aware recon framework. The honeypot is not Cowrie — it's a custom Python implementation — so every check returned empty. The framework got a false negative and proceeded with its payload. A Cowrie deployment presumably would have been fingerprinted as a honeypot and skipped. These sessions drove the T1497.001 row in the ATT&CK table, and their netstat -tulpn calls account for most of the T1049 (System Network Connections Discovery) count.

Section 11What You Should Do About It

Password authentication on SSH is the root cause of everything in this report. Disable it. Open your SSH server configuration at /etc/ssh/sshd_config and set PasswordAuthentication no. Generate an SSH key pair with ssh-keygen -t ed25519, add the public key to ~/.ssh/authorized_keys on your server, and confirm you can log in with the key before restarting the SSH service. Once key authentication works, no brute-force wordlist in the world can get in without your private key.

Moving SSH off port 22 reduces noise, not risk. Port 22 is the default. Move SSH to a high-numbered port (above 1024, something non-obvious), and automated scanners targeting port 22 will stop knocking. This is not a security control. A determined attacker will port-scan you. But it reduces log volume and eliminates low-effort commodity scanning from most of your authentication logs, which makes genuine threats easier to see.

If you are running Azure, audit your azureuser account immediately. azureuser was the second-most targeted username in this dataset, behind only root. Azure creates this account by default on Linux VMs. If your VM still has azureuser with password authentication enabled, your login credentials are being tried by automated tools right now. Rename the account, disable password auth, and restrict SSH access to known source IPs using Azure Network Security Groups if possible.

The Solana lure mostly didn't change attacker behavior. The honeypot was disguised as a Solana validator, but the majority of attackers treated it as a generic Linux server — credential stuffing, miner deployment, and reconnaissance scripts that are identical on any target. The first attacker used username sol and ran GPU enumeration commands (GPU hunting is relevant to crypto mining, not specifically to Solana validators, which do not require GPUs). Only 5 sessions out of 136,128 reached the wallet.json trap. The crypto_related password category (103 sessions) is an upper bound — the classifier catches partial substrings and may overcount. The miner-eviction loop killed processes running under the solana system user, but that is a generic account name in Linux Solana installs, not Solana-specific tooling. What the data supports: SSH-exposed servers are targeted by automated miner-deployment campaigns regardless of what they claim to be, and Solana infrastructure operators face the same baseline SSH risk as any internet-facing Linux server.

Most traffic came from rented hosting infrastructure, not residential botnets. After correcting the ASN classification (see methodology), 59.0% of sessions (80,340) originated from hosting providers, VPS platforms, and CDN/transit networks. The 41.0% residential and ISP traffic is substantial but not dominant. This suggests that most automated scanning and credential-validation campaigns are being run from rented cloud infrastructure — cheap, fast, and disposable — rather than compromised home devices.

A rapid-fire series of successful authentications with no subsequent activity is an active-attack signal, not a normal login pattern. Standard intrusion detection focuses on failed authentication (the "too many wrong passwords" pattern). The 38[.]58[.]169[.]236 event in this dataset produced 8,949 successful authentications in 8 hours with zero exploitation. Traditional fail-ban tools would not have flagged it. Configure monitoring to alert on any IP that authenticates successfully more than a threshold number of times (five is reasonable) within a short window, especially if session depth (command count) stays at zero or one.

After any suspected compromise, check cron and systemd before you check anything else. The miner deployment campaign in this dataset established persistence through two mechanisms: a crontab entry and a systemd unit file named watcher-netai.service. Run crontab -l for each user account, check /etc/cron.d/, review systemctl list-units --type=service for unfamiliar service names, and inspect /etc/systemd/system/ for unit files you did not create. Also check /dev/shm for binaries: any executable file in an in-memory filesystem location is suspicious by default. A file named astats in /dev/shm is a specific indicator for the campaign documented in this report.

Section 12Limitations

The honeypot is detectable. Sophisticated attackers running fingerprinting tools can identify a simulated SSH shell. A real Linux system responds differently than a scripted honeypot in edge cases. Attackers who detected the honeypot would have either left or changed their behavior. The dataset captures behavior from attackers who did not detect the simulation, or who continued anyway. The true distribution of attacker sophistication in the wild may differ from what is represented here.

AbuseIPDB was not populated during the run. This report does not include reputation scores from AbuseIPDB or similar threat intelligence platforms. Cross-referencing the top IPs against known-malicious registries would strengthen the IOC section but was not part of the data collection process.

The crypto_related password classifier overcounts. The 103 passwords flagged as crypto-related include partial string matches. Any password containing substrings that happen to overlap with cryptocurrency terms (coin names, wallet-related words, or common token tickers) would be captured by this classifier. The 103 figure should be treated as an upper bound, not a precise count of passwords crafted with cryptocurrency systems in mind.

Geolocation carries uncertainty. IP-to-country attribution uses the registered location of the IP block, not the physical location of the device or operator. VPNs, proxy servers, and Tor exit nodes can place an attack's apparent origin in a country that has nothing to do with the actual operator. Country-level statistics in this report describe where traffic came from, not where attackers are.

Comparison to prior reports requires caution. This report is the definitive record of the full 147-day run. Interim reports produced during the run period used different exclusion sets, different run-length denominators, and in some cases included the 38[.]58[.]169[.]236 sessions in hourly distribution data. Numbers from prior reports should not be compared to numbers in this report without accounting for these differences.

The shell simulation affects command data. The honeypot responded to commands with scripted output, not real system responses. Attackers may have issued different follow-on commands than they would have on a real system based on the simulated responses they received. Command counts and sequences reflect behavior in a simulated environment.

The miner campaign skews command-count statistics. The 93-command miner deployment script ran in 3,210 sessions, contributing a concentrated volume of specific commands. Any command that appears in that script (readlink, kill, chmod, crontab operations, systemd writes) is skewed upward in the overall command frequency table. The top-10 command list is partially a portrait of that single campaign rather than a representative cross-section of all attacker activity.

Closing

147 days of data collected while doing absolutely nothing except existing on the internet with port 22 open. No provocation. No interaction. Just presence. The internet sent 136,128 sessions, 414,070 commands, and one very motivated French-speaking backdoor architect who probably thought they were having a great Thursday.

The lesson is the same one it has always been, and it will still be the same lesson in 147 more days: password authentication on SSH is a door that millions of automated tools know how to knock on, and they will never stop knocking
